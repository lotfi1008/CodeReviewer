# انتشار نتیجهٔ بازبینی در GitLab

پس از ذخیرهٔ Review تکمیل‌شده، سامانه نتیجه را خودکار منتشر می‌کند. اجرای ناقص، لغوشده یا timeout منتشر نمی‌شود. خطای انتشار وضعیت Completed و یافته‌های ذخیره‌شده را از بین نمی‌برد؛ در صفحهٔ سوابق دکمهٔ «انتشار / همگام‌سازی کامنت روی MR» تلاش مجدد را بدون فراخوانی مدل انجام می‌دهد.

- Summary فارسی شامل شناسهٔ اجرا، SHA، مدل، پروفایل، تعداد فایل، محدودهٔ بررسی و یافته‌هاست. صفر یافته به معنی تأیید کل MR نیست.
- برای هر پروفایل، یک Summary متعلق به حساب متصل به‌روزرسانی می‌شود. پروفایل تشخیصی یک‌فایلی، خلاصهٔ پروفایل کامل را بازنویسی نمی‌کند.
- یافته‌ها به خط افزودهٔ معتبر در Diff متصل می‌شوند؛ مسیر قبل و بعد از تغییر نام حفظ می‌شود.
- Fingerprint از SHA، مسیر، خط، دسته و عنوان نرمال‌شده ساخته می‌شود. تکرار همان نتیجه کامنت دوباره ایجاد نمی‌کند؛ تشخیص معنایی یافته‌هایی با عنوان متفاوت انجام نمی‌شود.
- قبل از هر نوشتن، وضعیت opened و SHA از GitLab دوباره خوانده می‌شود. API کامنت شرط اتمیک SHA ندارد؛ امکان Push در فاصلهٔ خواندن و نوشتن صفر نیست. Inline به SHA مشخص متصل است و Summary نیز SHA را آشکارا نشان می‌دهد.
- همهٔ صفحات کامنت‌ها تا سقف ۱۰۰ صفحه خوانده می‌شوند؛ رسیدن به سقف، انتشار را متوقف می‌کند. کامنت حساب‌های دیگر تغییر داده نمی‌شود.
- متن مدل به‌صورت نقل‌قول و HTML-encoded ارسال می‌شود تا Quick Action و mention اجرا نشود.
- ثبت وضعیت، زمان و لینک انتشار در SQL Server در SourceSnapshots با Scope برابر publication:{runId} انجام می‌شود؛ رویدادهای هر تلاش در ReviewEvents نگهداری می‌شوند.
- قفل انتشار متعلق به همین میزبان است؛ اجرای چند میزبان هم‌زمان پشتیبانی نمی‌شود. توقف برنامه در میانهٔ انتشار ممکن است بخشی از کامنت‌ها را منتشر کرده باشد؛ تلاش مجدد آن‌ها را از GitLab بازخوانی می‌کند.
- انتشار GitHub هنوز پشتیبانی نمی‌شود و پیام مشخص در لاگ دارد.

مرجع قرارداد API: [GitLab Discussions](https://docs.gitlab.com/api/discussions/) و [GitLab Notes](https://docs.gitlab.com/api/notes/).

آزمون واقعی ۲۰ سپتامبر ۲۰۲۶: نتیجهٔ یک‌فایلی اجرای a9bf8214-ba1d-4feb-b2e4-d7c9dbe13fc8 روی MR شمارهٔ ۴ با note_id=18 و HTTP 201 منتشر شد. تلاش دوم فقط GET انجام داد و همان note_id را برگرداند. Inline روی سرور شبیه‌سازی‌شده آزموده شد؛ اجرای واقعی صفر یافته داشت.
# انتشار تدریجی و تصمیم بازبینی

از این نسخه، پس از تکمیل هر فایل، نتیجهٔ فعلی در SQL ذخیره و یافته‌های معتبر به Discussion خطی روی همان فایل و خط افزوده منتشر می‌شوند. Summary مشترک هر پروفایل به‌روزرسانی می‌شود. در اجرای ناقص نیز کامنت‌های معتبر قابل انتشارند، با هشدار صریحِ پوشش ناقص.

برای هر MR و پروفایل، یک Commit Status مستقل با نام `code-reviewer/mr-{number}/{profileId}` و یک برچسب اختصاصی MR همگام می‌شود:

- در حال اجرا و بدون ایراد مسدودکننده: `running`.
- وجود یافته با شدت حداقل `BlockingSeverity` (پیش‌فرض medium): `failed` و برچسب «نیازمند اصلاح».
- پایان موفق، بدون ایراد مسدودکننده: `success` و برچسب «بررسی شد».
- timeout، خطا، لغو یا پوشش ناقص: `failed`؛ Summary صریحاً ناقص بودن را نمایش می‌دهد.

موفقیت این Check به معنی اجرای Build/Test یا Approve انسانی نیست. این نسخه وضعیت Check و برچسب MR را تغییر می‌دهد؛ قابلیت بومی Request Changes/Approval جداگانهٔ GitLab را فراخوانی نمی‌کند. جلوگیری قطعی از Merge به تنظیمات پروژه برای الزامی‌بودن Checkها بستگی دارد. برچسب‌های دیگر، رأی سایر بازبین‌ها و وضعیت باز/بستهٔ MR تغییر نمی‌کنند.

SHA و باز بودن MR پیش از نوشتن کنترل می‌شود. تلاش مجدد، کامنت خطی یا Summary تکراری نمی‌سازد. اگر مجوز وضعیت یا برچسب کافی نباشد، انتشار کامل موفق اعلام نمی‌شود و خطا در SQL ثبت می‌شود.

آزمون واقعی روی گزارش `7b9f3ff1-0d71-4351-a9b0-265ff6af817e`: GitLab تغییر SHA یا وضعیت MR را گزارش کرد؛ نوشتن روی نسخهٔ قدیمی پیش از اولین کامنت متوقف شد. آزمون خودکار انتشار تدریجی، خط دقیق، rename، تکرار، برچسب‌های موجود، آستانهٔ شدت و وضعیت ناقص موفق بود. تأیید نوشتن واقعی این قابلیت به Review جدید روی MR باز با SHA جاری نیاز دارد.

منابع: [Commit Status API](https://docs.gitlab.com/api/commits/#set-commit-pipeline-status)، [MR Reviews](https://docs.gitlab.com/user/project/merge_requests/reviews/).
