# قوانین عمومی و اختصاصی بازبینی — نمونهٔ DMP

## وضعیت واقعی نسخهٔ فعلی

| نیاز | وضعیت | محل تنظیم |
|---|---|---|
| پرامپت مشترک، شدت، اطمینان و حوزه‌ها | پیاده شده | `/profiles`، جدول `ReviewProfiles` |
| دستور اختصاصی امنیت، دیتابیس، سازگاری و سایر حوزه‌ها | پیاده شده | `Domains[].Instructions` در همان پروفایل |
| قواعد کسب‌وکار و معیار پذیرش | پیاده شده | `BusinessRules`؛ حوزهٔ `business` باید فعال باشد |
| شناخت محصول و نگاشت مسیر به قابلیت | پیاده شده | `/project-context`؛ کلید اتصال + مخزن در SQL |
| اتصال خودکار پروفایل به مخزن و ارث‌بری قواعد عمومی | پیاده نشده | فعلاً انتخاب دستی پروفایل در هر اجرا |
| خواندن قوانین از فایل مخزن در SHA مورد بررسی | پیاده نشده | طرح `add-repository-review-policy` |
| تقدم سازمان ← مخزن ← تنظیمات اجرا و محدودیت غیرقابل تضعیف | پیاده نشده | همان طرح؛ وظایف هنوز انجام نشده‌اند |

پروفایل و نقشهٔ مخزن در اجرای Review snapshot می‌شوند. این با snapshot سیاست مؤثر سه‌لایه تفاوت دارد؛ آن قابلیت هنوز موجود نیست. `ProjectContext` دادهٔ مرجع است، جای دستورهای بازبینی نیست. موتور فعلی به شواهد از Diff نیاز دارد و خواندن فایل‌های خارج از Diff یا اثبات مسیر فراخوانی کل مخزن را انجام نمی‌دهد.

## محل مناسب نگهداری

پیشنهاد طراحی: قواعد ثابت سازمان در سامانه مدیریت شوند؛ قواعد خاص پروژه در مخزن نسخه‌پذیر باشند و سامانه آن‌ها را در commit بررسی‌شده بخواند. محدودیت سازمان بر مخزن مقدم باشد و تنظیمات هر اجرا فقط گزینه‌های مجاز را تغییر دهد. نتیجهٔ ترکیب با نسخه و hash در گزارش ذخیره شود. این طراحی در OpenSpec موجود است، ولی هنوز قابل استفاده نیست؛ نام و schema نهایی فایل را باید در همان پیاده‌سازی تثبیت کرد.

در نسخهٔ فعلی لازم نیست فایل قوانین داخل مخزن باشد. قرار دادن `AGENTS.md` یا اسناد قواعد در مخزن هم باعث خواندن خودکارشان توسط سرویس Review نمی‌شود. برای استفادهٔ امروز، متن قواعد را در پروفایل وارد کنید. اسناد DMP می‌توانند مرجع نسخه‌پذیر باقی بمانند و متن پروفایل هنگام تغییرشان دستی به‌روز شود.

## نمونه‌های آماده برای امکانات فعلی

- [پروفایل عمومی](examples/review-rules/common-profile.json): نقطهٔ شروع برای همهٔ مخزن‌ها؛ صحت، امنیت، دیتابیس و سازگاری.
- [پروفایل DMP](examples/review-rules/dmp-profile.json): قواعد عمومی به‌علاوه قواعد واقعی DMP؛ مستقل است و به ارث‌بری خودکار متکی نیست.
- [نقشهٔ DMP](examples/review-rules/dmp-project-context.json): نگاشت چند قابلیت حساس به مسیرهای واقعی کد، با سناریوی دستی پیشنهادی.

JSON پروفایل‌ها قالب دادهٔ `ReviewProfile` است؛ UI فعلی دکمهٔ import JSON ندارد. در `/profiles` پروفایل جدید بسازید، نام و Prompt و تنظیمات را از نمونه کپی کنید، حوزه‌های `Domains` را فعال و متن هر `Instructions` را در «دستور تکمیلی این حوزه» قرار دهید. برای DMP حوزهٔ بیزینس را نیز فعال و `BusinessRules` را کپی کنید. مدل را هنگام اجرا انتخاب کنید. حداقل شدت `medium` و اطمینان `0.85` تنظیم پیشنهادی نمونه‌اند، نه تصمیم مصوب DMP.

نقشهٔ JSON را می‌توان مستقیماً در `/project-context` پس از انتخاب اتصال و مخزن DMP وارد و ذخیره کرد. سپس در داشبورد/میز بازبینی، پروفایل «DMP — قواعد عمومی و اختصاصی» را دستی انتخاب کنید. نمونه‌ها صرفاً فایل آماده‌اند؛ در دیتابیس محیط جاری ثبت نشده‌اند.

تغییر پروفایل عمومی، پروفایل DMP را خودکار به‌روز نمی‌کند. هر دو باید هنگام تغییر قواعد مشترک همگام شوند. پروفایل DMP از نظر فنی برای مخزن دیگری هم قابل انتخاب است؛ UI فعلی این انتخاب را محدود نمی‌کند.

## مبنای DMP و حدود نمونه

نمونه از checkout محلی `D:/Sources/DMP` در ۲۰۲۶-۱۰-۰۸ استخراج شده است:

- `docs/architecture/ARCHITECTURE_RULES.md`: ARC-DOM-002، ARC-APP-003، ARC-END-003، ARC-COMP-001/002.
- `docs/security/SECURITY_RULES.md`: SEC-002/003/005/008، SEC-TOK-003، SEC-GRID-001/002/006، SEC-FORM-002/004/005، SEC-PBI-001/002/003.
- `docs/engineering/CODING_RULES.md`: CODE-LOG-003/005/007 و CODE-FE-004.
- `DMP.sln`: مرجع پروژه‌های فعال؛ MVC و BlazorServer هر دو در solution حاضرند. توصیف قدیمی معماری که فقط MVC را فعال می‌داند، مبنای حذف Blazor از نمونه قرار نگرفته است.

نقشه عمداً کامل نیست و برای Accounts، Roles/RolePermissions، GridReports و Dashboards/PBI تهیه شده است. UiPath خالی است تا مسیر UI حدس زده نشود. سناریوها پیشنهاد بررسی دستی‌اند و اجرا نشده‌اند. ویژگی `Critical` بر برآورد ریسک اثر می‌گذارد؛ به معنی اثبات ایراد نیست. مسیرها باید با شاخهٔ واقعی مخزن مقصد هم تطبیق داده شوند.

قواعد معماری و سبک به‌تنهایی تضمین نمی‌کنند موتور فعلی یافته بدهد: موتور گزارش را به ایراد مستند با اثر اجرایی محدود می‌کند. نقض ساختار بدون اثر قابل اثبات ممکن است گزارش نشود. قواعد `TARGET` اسناد DMP، مثل اجباری‌کردن Outbox یا نسخه‌بندی فرم، به‌عنوان الزام اجرایی وارد نمونه نشده‌اند.

## مثال رفتار بازبینی

| تغییر فرضی | قاعده | انتظار |
|---|---|---|
| جایگذاری مقدار ورودی کاربر در متن SQL با Replace | SEC-GRID-002 | با وجود شاهد در Diff و مسیر اجرای معلوم، گزارش خطر تزریق و پیشنهاد پارامتر نوع‌دار |
| تولید لینک محافظت‌شدهٔ گزارش با URL دلخواه کاربر | SEC-PBI-001/002 | بررسی کنترل مجوز منبع و استفاده از BusinessId معتبر |
| افزودن token به لاگ | SEC-005 | گزارش افشای دادهٔ حساس با نقل کوتاه فاقد مقدار واقعی secret |
| تغییر صرفاً نام یک متغیر | قواعد عمومی نمونه | بدون یافتهٔ سلیقه‌ای |
| الزام Outbox فقط بر اساس هدف آیندهٔ معماری | ARC-DATA-008 [TARGET] | بدون ادعای الزام فعلی |

این‌ها مثال‌اند، نه یافته از MR واقعی. دستور مدل نیز جای کنترل قطعی امنیت داده در سامانه را نمی‌گیرد.

## منابع پیاده‌سازی در همین سامانه

- `src/CodeReviewer.Web/Services/ReviewProfile.cs` و `ReviewDomain.cs`: فیلدها و اعتبارسنجی.
- `src/CodeReviewer.Web/Components/Pages/Profiles.razor`: فرم ورود قواعد.
- `src/CodeReviewer.Web/Services/ProjectContext.cs`: نقشه و ذخیرهٔ مستقل هر مخزن.
- `src/CodeReviewer.Web/Services/AiReviewService.cs`: ترکیب Prompt و دستور حوزه؛ قواعد بیزینس فقط در گروه دارای حوزهٔ business ارسال می‌شوند.
- `src/CodeReviewer.Web/Services/SourceControlService.cs`: قرارداد فعلی فاقد خواندن فایل دلخواه در commit است.
- `openspec/changes/add-repository-review-policy/`: طراحی و وظایف قابلیت آینده.
