# AI Code Reviewer

## گزارش کم‌نویز و تحلیل اثر (نسخهٔ جاری)
یافته‌ها به شاهد عینی از تغییر، اثر مشخص و اقدام اصلاحی نیاز دارند. خروجی توسعه‌دهنده شامل ایرادهای مهم، اثر قابلیت‌ها، تست دستی و آمادگی انتشار است؛ روایت فایل‌ها و اطلاعات داخلی در گزارش عادی نیست. Context در `/project-context` برای هر مخزن در SQL تنظیم می‌شود. مستندات و فایل‌های تولیدشده پیش‌فرض از تحلیل اجرایی کنار می‌روند و حوزه‌ها بر اساس ارتباط مسیریابی می‌شوند. توضیحات بخش‌های قدیمی‌تر دربارهٔ تحلیل همهٔ فایل‌های متنی با این سیاست جایگزین شده است. [معماری، تغییرات، آزمون‌ها و محدودیت‌ها](docs/high-signal-review.md).

سامانه در حال ساخت برای بررسی Merge Requestهای GitLab Self-Managed با Blazor Server و مدل داخلی است.

## OpenSpec

راهنمای [قوانین عمومی و اختصاصی بازبینی و نمونه‌های آمادهٔ DMP](docs/repository-review-rules.md) روش استفاده از پروفایل و نقشهٔ مخزن در نسخهٔ فعلی، و تفاوت آن با قابلیت آیندهٔ قوانین نسخه‌پذیر Repository را توضیح می‌دهد.

Spec قابلیت‌های جدید و Changeهای فعال در [openspec](openspec/) نگهداری می‌شوند. در Codex از `$openspec-propose` برای پیشنهاد Change جدید، از `$openspec-apply-change` برای پیاده‌سازی یک Change تأییدشده و از `$openspec-archive-change` فقط پس از تکمیل و تأیید پیاده‌سازی استفاده کنید. اسناد `docs` راهنماهای عملیاتی و گزارش‌های تاریخی پروژه باقی می‌مانند.

## اجرای UI محلی

```powershell
dotnet run --project src/CodeReviewer.Web
```

در صفحه **مدیریت اتصال‌ها** می‌توانید چند اتصال GitLab یا GitHub و چند مدل AI را اضافه، ویرایش، آزمایش، حذف و یکی را به‌عنوان پیش‌فرض انتخاب کنید. سپس در داشبورد، اتصال سورس کنترل، مخزن و مدل را انتخاب کنید؛ MRهای باز بدون وارد کردن لینک نمایش داده می‌شوند. نتیجه و خطای هر بررسی در SQL Server و صفحهٔ **سوابق بازبینی** ذخیره می‌شود.

پروتکل‌های مدل در این نسخه: endpoint سازگار با OpenAI Chat Completions، Azure OpenAI و Ollama از طریق API سازگار با OpenAI. همه مدل‌ها پشت `IChatClient` قرار دارند. قابلیت JSON Schema برای هر اتصال قابل تنظیم است. اجرای مدل هنوز به endpoint و اعتبارنامه واقعی نیاز دارد.

در فرم اتصال مدل، پس از وارد کردن نشانی پایه و کلید API، دکمهٔ «دریافت مدل‌ها از API» فهرست را در دراپ‌داون بارگذاری می‌کند. درخواست روی سرور برنامه با مسیر `models` نسبت به همان نشانی پایه و همان سیاست گواهی ارسال می‌شود؛ ذخیرهٔ اتصال و نام مدل از قبل لازم نیست. هنگام ویرایش، کلید ذخیره‌شده فقط برای همان نشانی و نوع سرویس استفاده می‌شود. با تغییر نشانی/کلید فهرست قبلی پاک می‌شود. شناسهٔ فعلی حفظ می‌شود و ورود دستی نیز موجود است. در Azure نام Deployment دستی وارد می‌شود؛ فهرست مدل‌ها معادل Deploymentها نیست. وجود شناسه در فهرست تضمین‌کنندهٔ قابلیت گفتگو یا JSON Schema نیست.

مبنای پروتکل فهرست: [OpenAI Models API](https://platform.openai.com/docs/api-reference/models) و [Ollama OpenAI compatibility](https://github.com/ollama/ollama/blob/main/docs/api/openai-compatibility.mdx).

اطلاعات اتصال در جدول Connections ذخیره می‌شود و فقط توکن‌ها و کلیدهای API با ASP.NET Core Data Protection رمزگذاری می‌شوند. مسیر پایه از `Storage:DataDirectory` در appsettings خوانده می‌شود (پیش‌فرض `D:/CodeReviewer/Data`) و کلیدهای رمزگذاری در زیرپوشهٔ `keys` آن قرار دارند؛ مسیر باید مطلق و قابل نوشتن باشد؛ از پایگاه داده و کلیدها با هم پشتیبان بگیرید. در محیط Production دسترسی به UI به احراز هویت Windows نیاز دارد؛ IIS باید Windows Authentication داشته باشد.

محیط Development از SQL Server محلی و دیتابیس `CodeReviewer` با Windows Integrated Authentication استفاده می‌کند. دیتابیس باید پیش از اجرا ساخته شود؛ برنامه جدول‌ها را ایجاد می‌کند. مقدار `TrustServerCertificate=True` فقط برای SQL محلی توسعه تنظیم شده است. در Production مقدار `ConnectionStrings__CodeReviewer` با گواهی معتبر و حساب محدود تنظیم شود. طبق تنظیم فعلی، `ServiceConnections:AllowUntrustedCertificates=true` اعتبارسنجی گواهی سرور را برای GitLab، GitHub، OpenAI-compatible، Azure OpenAI و Ollama غیرفعال می‌کند؛ رمزگذاری HTTPS برقرار می‌ماند، ولی هویت سرور از روی گواهی تأیید نمی‌شود. برای اعتبارسنجی استاندارد مقدار را `false` کرده و برنامه را راه‌اندازی مجدد کنید. این تنظیم متعلق به همین سامانه است و تنظیمات Windows یا مرورگر را تغییر نمی‌دهد. ابزار Phase0Probe نیز گواهی داخلی را می‌پذیرد؛ برای بررسی استاندارد متغیر `REVIEW_ALLOW_UNTRUSTED_CERTIFICATES=false` را تنظیم کنید.

این نسخه یک میزبان دارد؛ بازیابی اجراهای قطع‌شده در شروع همان میزبان انجام می‌شود و اجرای چند نمونهٔ هم‌زمان هنوز پشتیبانی نمی‌شود. تاریخچه حداکثر ۱۰۰ اجرای اخیر را نمایش می‌دهد، ولی رکوردهای قدیمی‌تر از SQL حذف نمی‌شوند. MR مشاهده‌شده در مرورگر با SHA خالی به‌عنوان snapshot اولیه ثبت شده؛ برای اجرای بررسی باید از API همگام‌سازی شود.

## وضعیت پیاده‌سازی

- آماده: پنل فارسی و راست‌به‌چپ با فونت وزیرمتن محلی، ثبت رمزگذاری‌شده اتصال‌های چندگانه، آداپتور GitLab و GitHub، انتخاب مدل در زمان اجرا، فهرست پروژه‌ها و MRهای باز، Review دستی C# با `IChatClient`، نمایش یافته‌های فیلترشده.
- آماده: SQL Server برای اتصال‌ها، تنظیمات پیش‌فرض، snapshot مخزن/MR/Diff، وضعیت اجرا، یافته‌ها و آزمایش اتصال؛ صفحهٔ سوابق و ثبت قطع شدن اجرای قبلی.
- آماده برای GitLab: انتشار اختیاری Summary، یافته‌های Inline، وضعیت و برچسب‌ها فقط با انتخاب چک‌باکس «کامنت‌گذاری و ارسال نتیجه» هنگام شروع Review؛ کنترل Head SHA و جلوگیری از تکرار در میزبان واحد.
- در ادامه: دریافت خودکار Webhook، Roslyn، قوانین Repository و انتشار نتایج در GitHub.
- وابسته به زیرساخت: گواهی قابل اعتماد GitLab و endpoint مدل داخلی. وضعیت فاز ۰ در [docs/phase-0.md](docs/phase-0.md) ثبت شده است.

اطلاعات ورود GitLab در مرورگر به سرویس API منتقل نمی‌شود. برای سرویس باید توکن API جداگانه در UI ثبت شود.

## میز بازبینی دستی

در `/profiles` پروفایل‌های بازبینی ذخیره می‌شوند. سه نقطهٔ شروع «سریع و سبک»، «متعادل» و «دقیق و سخت‌گیرانه» قابل ویرایش و کپی هستند. مدل پیشنهادی، پرامپت، سخت‌گیری، حداقل شدت و اطمینان، حوزه‌ها، مدل هر حوزه، اندازهٔ هر بخش Diff و مهلت پاسخ قابل تنظیم‌اند. در داشبورد و میز بازبینی پروفایل و مدل هر اجرا را انتخاب کنید. اجرای مجدد با تنظیمات دیگر گزارش مستقلی ایجاد می‌کند؛ حوزه‌های دارای مدل یکسان در یک فراخوانی بررسی می‌شوند و فایل‌ها با هم‌زمانی قابل تنظیم پردازش می‌شوند. تنظیمات کامل هر اجرا در `ReviewRuns.Profile` و پروفایل‌های قابل ویرایش در `ReviewProfiles` ذخیره می‌شوند. موتور همهٔ فایل‌های دارای Diff متنی را بررسی می‌کند؛ محدودیت تعداد فایل و پسوند C# برداشته شده است.

نمای Diff کد را چپ‌به‌راست با شمارهٔ خطوط قدیم و جدید، رنگ افزوده/حذف‌شده، انتخاب خط برای یادداشت، جست‌وجوی فایل، شکستن خطوط بلند، اندازهٔ فونت و نمای بزرگ نمایش می‌دهد.

لینک‌های GitLab از مسیر برگشتی API و میزبان/پورت اتصال تنظیم‌شده ساخته می‌شوند تا `external_url` داخلی سرور کاربر را به آدرس غیرقابل‌دسترسی نفرستد. میز بازبینی با queryهای `source`، `repo` و `number` به همان درخواست لینک مستقیم دارد؛ گزارش اجرا نیز با `/history?run=<id>` باز می‌شود.

اجراهای جدید Review، مرحلهٔ دریافت Diff و کنترل SHA، انتخاب فایل‌ها، ارسال هر فایل، انتظار پاسخ (هر ۵ ثانیه)، اعتبارسنجی و ذخیرهٔ نتیجه را در `ReviewEvents` ثبت می‌کنند. پنل زنده هر ۲ ثانیه آخرین ۲۰۰ رویداد را می‌خواند و پیشرفت بر اساس فایل‌های تکمیل‌شده نمایش داده می‌شود. لاگ عملیاتی شامل کلید API یا متن خام پاسخ مدل نیست. لغو و پایان مهلت نیز وضعیت پایانی دارند. اجرا در صف SQL انجام می‌شود و با بسته‌شدن مرورگر ادامه دارد. بعد از توقف میزبان، کار ناتمام از ابتدا اجرا می‌شود.

در `/requests` می‌توانید فهرست ذخیره‌شدهٔ MR/PRها را جست‌وجو و همهٔ درخواست‌های باز مخزن انتخاب‌شده را همگام‌سازی کنید. عنوان، نویسنده، توضیحات، شاخه‌ها و Head SHA نمایش داده می‌شوند. دریافت Diff قبل و بعد از دانلود، یکسان بودن Head SHA را کنترل می‌کند؛ تغییر نسخه نیازمند همگام‌سازی مجدد است. دریافت فایل‌ها صفحه‌بندی می‌شود و سقف داخلی تعداد فایل ندارد؛ محدودیت‌های Diff سرویس مبدأ در گزارش پوشش مشخص می‌شوند.

بازبینی دستی بدون مدل انجام می‌شود: یادداشت عمومی یا یادداشت فایل با شمارهٔ خط افزوده، و جمع‌بندی «بررسی شد / نیازمند اصلاح / نیازمند گفتگو». همهٔ موارد با نویسنده، زمان و نسخه در جدول `ReviewEntries` ذخیره می‌شوند. این جمع‌بندی‌ها صرفاً داخلی‌اند و approve، merge یا comment در سرویس مبدأ ایجاد نمی‌کنند.

کمک AI اختیاری است و در صفحهٔ «پرسش از AI» به شکل گفتگو برای فایل و Head SHA انتخاب‌شده نمایش داده می‌شود. مدل فعال، پرسش، حداکثر چهار نوبت اخیر گفتگو و تمام Diff همان فایل را در بخش‌های ۱۲٬۰۰۰ کاراکتری دریافت می‌کند؛ پرسش، پاسخ و نام مدل در `ReviewEntries` با منشأ `AiHelp` ذخیره می‌شوند و گفتگوهای قدیمی نیز قابل نمایش‌اند. مهلت پاسخ هر بخش ۶۰ ثانیه است. برای دریافت Diff به اتصال API سورس کنترل، و برای کمک AI به اتصال مدل نیاز است؛ این گفتگو هیچ چیزی روی MR/PR منتشر نمی‌کند.

آزمون‌ها: `dotnet test tests/CodeReviewer.Web.Tests`؛ آزمون‌های SQL به SQL Server محلی با مجوز ساخت دیتابیس نیاز دارند. دیتابیس موقت با پیشوند `CodeReviewerTest_` ساخته و فقط همان دیتابیس آزمایشی پاک می‌شود.

مهلت مدل: `ModelTimeoutSeconds` در هر پروفایل (پیش‌فرض ۱۲۰، محدوده ۵ تا ۶۰۰ ثانیه) زمان دریافت پاسخ کامل برای هر تلاش از هر بخش را محدود می‌کند. مهلت کل پروفایل نیز برقرار است. انتظار با `WaitAsync` قطع می‌شود حتی اگر سرویس لغو را رعایت نکند؛ توقف محاسبه در سرور بیرونی قابل تضمین نیست. تعداد تلاش مجدد با `ModelRetryCount` در پروفایل و صفحهٔ شروع بازبینی قابل تنظیم است (پیش‌فرض ۳، محدودهٔ ۰ تا ۱۰؛ علاوه بر درخواست اولیه). هر بخش برای هر مدل این مقدار را مستقل اعمال می‌کند. خطاهای موقت شبکه، HTTP مانند 429 و 503 و پایان مهلت پاسخ با فاصلهٔ ۵، ۱۰، ... ثانیه تکرار می‌شوند؛ هر تلاش مهلت پاسخ مستقل دارد و مهلت کل اجرا و لغو کاربر همهٔ تلاش‌ها و فاصله‌ها را محدود می‌کنند. خطای هر تلاش، از جمله آخرین تلاش، با نام مدل و شمارهٔ بخش در لاگ درخواست ثبت می‌شود؛ خطای احراز هویت و پاسخ نامعتبر تکرار نمی‌شوند. پایان مهلت با وضعیت `TimedOut`، لغو کاربر با `Cancelled` و خطای سرویس با `Failed` ذخیره می‌شود. در اجرای ناقص، یافته‌های معتبر فایل‌های تکمیل‌شده نگهداری می‌شوند. آزمایش مدل حداکثر ۳۰ ثانیه و پرسش کمکی حداکثر ۶۰ ثانیه منتظر پاسخ می‌ماند. اجرای دوباره با انتخاب مدل یا پروفایل دیگر به تصمیم کاربر انجام می‌شود.

فهرست درخواست‌ها، تغییرات، شروع بازبینی، لاگ، گزارش و انتشار مسیرهای اختصاصی دارند.


## پنل جدید و گزارش کاربردی

فهرست‌ها و فرم‌ها، گزارش اجرا، لاگ و پیش‌نمایش انتشار صفحهٔ اختصاصی دارند. سوابق از SQL Server صفحه‌بندی می‌شود و گزارش با شناسهٔ مستقیم حتی خارج از صفحهٔ فعلی قابل دسترسی است. راهنمای مسیرها و تغییرات: [بازطراحی پنل](docs/ui-redesign.md). کامنت جدید توضیح تغییر هر فایل، تحلیل مدل و بررسی انسانی پیشنهادی را شامل می‌شود؛ نتیجهٔ خالی و فاقد تحلیل مستند منتشر نمی‌شود.


## اجرای عملیاتی و پروفایل چندحوزه‌ای

در ویرایش پروفایل می‌توانید امنیت، بیزینس، صحت عملکرد، کارایی، پایگاه داده، Async، مدیریت خطا، نگهداشت‌پذیری، تست و دسترس‌پذیری را با هم انتخاب کنید. هر حوزه مدل و دستور جدا دارد. حوزهٔ بیزینس نیازمند قواعد صریح شماست. پروفایل هر اجرا در SQL ثابت می‌ماند؛ ویرایش پروفایل، کارهای صف‌شده را تغییر نمی‌دهد.

Diff بزرگ به بخش‌های کامل شکسته می‌شود؛ ادامهٔ متن حذف نمی‌شود. فایل بدون Diff یا خطای مدل، وضعیت `Incomplete` ایجاد می‌کند و با نشان صریحِ بازبینی ناقص منتشر می‌شود؛ Check بازبینی موفق نخواهد شد. تعداد بخش‌های کامل و کل بخش‌ها در گزارش پوشش ذخیره می‌شود. لاگ HTTP دلیل قابل اقدام را بدون متن خام پاسخ سرویس یا کلید API ثبت می‌کند.

ساخت بسته: `powershell -File tools/Publish-Iis.ps1`. [راهنمای استقرار و آزمون پذیرش](docs/deployment.md). Worker فعلاً داخل میزبان وب است؛ راهنما تنظیمات لازم IIS برای یک نمونهٔ همیشه‌فعال را مشخص می‌کند. مقصد نهایی انتشار و قواعد واقعی بیزینس باید توسط مالک سامانه تعیین شوند.


انتشار تدریجی: یافته‌های معتبر پس از هر فایل روی خط مربوط در GitLab ثبت می‌شوند؛ وضعیت Check و برچسب MR با آستانهٔ شدت قابل تنظیم همگام می‌شوند. جزئیات در [راهنمای انتشار](docs/review-publication.md).
