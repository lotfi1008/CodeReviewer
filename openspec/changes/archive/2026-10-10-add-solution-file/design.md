# Design

## Context

انگیزه در [`proposal.md`](openspec/changes/add-solution-file/proposal.md:1) آمده است. وضعیت فعلی و قیدهای مؤثر بر طراحی:

- مخزن سه پروژهٔ مستقل دارد و هیچ فایل سولوشنی در آن نیست:
  - [`src/CodeReviewer.Web/CodeReviewer.Web.csproj`](src/CodeReviewer.Web/CodeReviewer.Web.csproj:1) — `Microsoft.NET.Sdk.Web`، `net10.0`.
  - [`tests/CodeReviewer.Web.Tests/CodeReviewer.Web.Tests.csproj`](tests/CodeReviewer.Web.Tests/CodeReviewer.Web.Tests.csproj:1) — `Microsoft.NET.Sdk`، `net10.0`، ارجاع به پروژهٔ وب.
  - [`tools/CodeReviewer.Phase0Probe/CodeReviewer.Phase0Probe.csproj`](tools/CodeReviewer.Phase0Probe/CodeReviewer.Phase0Probe.csproj:1) — `Microsoft.NET.Sdk`، `OutputType=Exe`، `net10.0`.
- README فعلی آزمون را با مسیر مستقیم پروژه توصیه می‌کند: `dotnet test tests/CodeReviewer.Web.Tests` ([`README.md`](README.md:60)).
- [`tools/Publish-Iis.ps1`](tools/Publish-Iis.ps1:3) انتشار را مستقیماً از مسیر `.csproj` وب انجام می‌دهد و طبق proposal تغییر نمی‌کند.
- [`gitignore.`](.gitignore:1) خروجی‌های `bin/` و `obj/` و پوشهٔ `artifacts/` را نادیده می‌گیرد؛ فایل سولوشن اثری بر آن ندارد.
- قالب انتخاب‌شدهٔ کاربر: `.slnx` (XML جدید) روی SDK مبتنی بر .NET 10.

## Goals / Non-Goals

**Goals:**

- یک نقطهٔ ورود واحد در ریشهٔ مخزن برای ساخت و آزمون بدون اشاره به مسیر پروژه‌ها.
- پوشش کامل و بدون ابهام هر سه پروژهٔ موجود.
- حداقل تغییر سطح: افزودن یک فایل جدید و یک به‌روزرسانی مستندات، بدون تغییر پروژه‌ها.

**Non-Goals:**

- ایجاد یا تغییر خط لولهٔ CI/CD، اسکریپت انتشار، یا تنظیمات استقرار.
- دسته‌بندی/فیلترگذاری ساخت (مثلاً configuration سفارشی) یا افزودن `Directory.Build.props`.
- افزودن پروژهٔ جدید یا تغییر مراجع بین پروژه‌ها.

## Decisions

### تصمیم ۱: قالب `.slnx` در ریشهٔ مخزن

فایل سولوشن در ریشهٔ مخزن با نام `CodeReviewer.slnx` و قالب XML جدید ساخته می‌شود.

- **چرا:** انتخاب صریح کاربر؛ `.slnx` روی .NET 10 پشتیبانی می‌شود، متن‌محور و سازگار با کنترل نسخه است و از تداخل فایل `.sln` کلاسیک با ابزارهای جدید پرهیز می‌کند.
- **گزینه‌های رد‌شده:**
  - `.sln` کلاسیک: سازگاری گسترده‌تر با ابزارهای قدیمی، ولی کاربر قالب جدید را انتخاب کرد.
  - ساخت هر دو قالب: پیچیدگی نگهداشت و احتمال واگرایی دو فایل؛ رد شد.
  - بدون فایل سولوشن (وضعیت فعلی): نیاز به مسیر مستقیم پروژه‌ها را حفظ می‌کند؛ رد شد.

### تصمیم ۲: ساختار سولوشن با پوشه‌های گروه‌بندی مسیر

پروژه‌ها درون گره‌های `Folder` بر اساس مسیر مخزن گروه‌بندی می‌شوند تا ترتیب با ساختار پوشه‌ها هم‌خوان باشد. شکل کلی فایل:

```xml
<Solution>
  <Folder Name="/src/">
    <Project Path="src/CodeReviewer.Web/CodeReviewer.Web.csproj" />
  </Folder>
  <Folder Name="/tests/">
    <Project Path="tests/CodeReviewer.Web.Tests/CodeReviewer.Web.Tests.csproj" />
  </Folder>
  <Folder Name="/tools/">
    <Project Path="tools/CodeReviewer.Phase0Probe/CodeReviewer.Phase0Probe.csproj" />
  </Folder>
</Solution>
```

- **چرا:** مسیرهای `Path` نسبی و منطبق بر ساختار واقعی مخزن هستند؛ گروه‌بندی خوانایی و پیمایش را بهتر می‌کند.
- **گزینه‌های رد‌شده:** فهرست تخت پروژه‌ها بدون `Folder`: ساده‌تر ولی برای رشد آینده خوانایی کمتری دارد.
- **نکتهٔ سازگاری:** قالب دقیق و مجاز `.slnx` باید با SDK هدف (`net10.0`) و ابزار خط فرمان استفاده‌شده در زمان پیاده‌سازی تأیید شود؛ در صورت نیاز ابزار، ساختار با `dotnet sln` بازنویسی می‌شود بدون تغییر در فهرست پروژه‌ها.

### تصمیم ۳: به‌روزرسانی حداقلی مستندات

فقط بخش ساخت و آزمون [`README.md`](README.md:60) برای معرفی سولوشن به‌عنوان نقطهٔ ورود پیشنهادی به‌روزرسانی می‌شود.

- **چرا:** مسیرهای فعلی باید معتبر بمانند؛ تغییر مستندات فقط مسیر پیشنهادی را اضافه می‌کند.
- **گزینه‌های رد‌شده:** بازنویسی کامل راهنمای ساخت/آزمون یا تغییر اسکریپت انتشار؛ فراتر از حوزهٔ این تغییر.

### تصمیم ۴: بدون تغییر در تنظیمات build مشترک

هیچ `Directory.Build.props`/`Directory.Packages.props` یا `global.json` جدیدی افزوده نمی‌شود.

- **چرا:** این تغییر فقط یک نقطهٔ ورود فراهم می‌کند و قید نسخهٔ SDK را به پروژه تحمیل نمی‌کند؛ افزودن آن می‌تواند رفتار ساخت موجود را تغییر دهد.
- **گزینه‌های رد‌شده:** افزودن `global.json` برای قفل نسخهٔ SDK: خارج از دامنهٔ درخواست و پرخطر برای سازگاری.

## Risks / Trade-offs

- [پشتیبانی ناهمگون ابزار از `.slnx` در نسخه‌های قدیمی‌تر SDK/IDE] → پیش‌نیاز در مستندات ذکر می‌شود؛ فرمان‌های مسیر مستقیم پروژه‌ها همچنان معتبر می‌مانند.
- [واگرایی فهرست پروژه‌ها با افزودن پروژهٔ جدید] → یک requirement صریح نگهداشت سولوشن را الزام می‌کند و در tasks یک گام بازبینی قرار می‌گیرد.
- [جزئیات دقیق قالب `.slnx`] → قالب با ابزار SDK در زمان پیاده‌سازی تأیید و در صورت نیاز با `dotnet sln` تولید می‌شود؛ فهرست پروژه‌ها منبع حقیقت است.
- [تغییر ناخواستهٔ رفتار ساخت] → هیچ فایل پروژه یا تنظیمات مشترک تغییر نمی‌کند؛ رفتار قدیمی با فرمان مستقیم پروژه آزمون می‌شود.

## Migration Plan

- **استقرار:** افزودن `CodeReviewer.slnx` و به‌روزرسانی README در یک commit؛ بدون مهاجرت داده یا تغییر پیکربندی.
- **بازگردانی (Rollback):** حذف فایل `CodeReviewer.slnx` و برگرداندن بخش README؛ هیچ اثری بر کد، پایگاه داده یا استقرار ندارد.
- **پایایی (Idempotency):** افزودن مکرر همان پروژه‌ها به سولوشن نباید رکورد تکراری ایجاد کند.
- **قابلیت مشاهده (Observability):** معیار پذیرش، موفقیت `dotnet build CodeReviewer.slnx` و `dotnet test CodeReviewer.slnx` است؛ خروجی فرمان‌ها شاهد پذیرش است.
